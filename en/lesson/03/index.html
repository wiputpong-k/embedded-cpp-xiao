Goal Organize names, and understand why C++ needs name mangling

C

Function names must be unique, so you write log_int, log_float, and an enum mixes with int anywhere.

C++

One name can be overloaded for different parameters, namespace prevents name clashes, and enum class never converts to int by itself and can set its size with : uint8_t.

  • overloading: several functions share one name but take different parameters (a different number or different types). The compiler picks the one that matches the arguments. Differing only in the return type does not count as an overload.
  • namespace: a box for names. It holds anything with a name, not just functions: variables, constants, enums and classes. You use it as box::name, e.g. logx::info.
  • enum class: an enum you must spell out in full, e.g. Mode::Slow, and that never turns into a number by itself. : uint8_t makes it take 1 byte.

namespace: no more name clashes

In C every name lives in one shared space. If two libraries both have a function called info, the build fails, so C programmers add a prefix by hand. C++ uses a namespace for this instead.

// C: add a prefix by hand to avoid clashes
void logx_info(const char* msg);
void wifi_info(const char* msg);

// C++: a namespace instead of a prefix
namespace logx {
  int level = 1;                // variables work too
  void info(const char* msg);
}
namespace wifi {
  void info(const char* msg);   // info again is fine: a different box
}

logx::info("boot");
wifi::info("connected");
  • A real example from this course: the Seeed core already has a class called RingBuffer, so lesson 10 keeps our RingBuffer in the namespace xiao and calls it xiao::RingBuffer, which avoids a clash with the core's.
  • std::, which you will see often, is also a namespace: the box of the C++ standard library, e.g. std::array.
  • A namespace is not a class: a namespace only groups names, and you cannot create an object from it. A class is a data type you create objects from (lesson 04).

How enum class differs from C's enum

An enum gives names to a fixed set of choices, such as modes or states. Underneath they are still the numbers 0, 1, 2 … C++ adds enum class, which is checked more strictly. Compare:

// C: a plain enum
enum Mode  { OFF, SLOW, FAST };
enum Speed { SLOW, FAST };      // error: SLOW again, the names leak out
enum Mode m = SLOW;
int x = m;                      // 1: silently turned into an int
if (m == 2) {}                  // compares with a number, but which mode is 2?

// C++: enum class
enum class Mode  : uint8_t { Off, Slow, Fast };   // : uint8_t = takes 1 byte
enum class Speed : uint8_t { Slow, Fast };        // no clash: the names stay in their own box
Mode m = Mode::Slow;                              // the full name is required
int x = m;                                        // error: no automatic conversion to int
int y = static_cast<int>(m);                      // convert on purpose
  • Names stay inside: C's enum makes SLOW a shared name for the whole file, so you add a prefix by hand, such as MODE_SLOW. enum class keeps its names in its own box, like a namespace.
  • No automatic conversion to a number: the compiler catches the bug of mixing a mode up with a number at compile time. When you really need the number, use static_cast<int>(m).
  • You can set its size: C's enum is the size of an int (4 bytes on the nRF52840). : uint8_t fixes the size, which helps when you store it in a struct, send it over Serial/BLE or save it to flash.

After compiling, both are just numbers, so enum class costs no speed. What you gain is stricter checking by the compiler.

When to use an enum

Use one when a value has a small set of choices known in advance, each with a meaning, and it is not a quantity you add or subtract. Common cases in firmware:

  • States of a state machine, e.g. Idle, Connecting, Connected (example below).
  • Modes or settings, e.g. Mode::Slow in this lesson, or log levels (Debug, Info, Error).
  • Events, e.g. Debouncer::Event::Pressed in lesson 07.
  • Results and error codes: Err::Timeout reads far better than return -3;.
  • Protocol commands, with numbers you set to match the spec, e.g. enum class Cmd : uint8_t { Ping = 0x01, ReadTemp = 0x10 };
enum class State : uint8_t { Idle, Connecting, Connected };
State state = State::Idle;

switch (state) {
  case State::Idle:       /* wait for button */     break;
  case State::Connecting: /* wait for link */  break;
  case State::Connected:  /* send data */    break;
}

Do not use an enum for quantities such as temperature, time, a pin number or a baud rate. Use constexpr for those (lesson 02). A simple rule: if you have to explain a number in a comment, as in if (state == 2) // 2 = connected, it should be an enum.

Name mangling: how overloading works

In C, a function called info is also called info in the .o file. C++ allows several info functions, so that name is not enough for the linker (lesson 01) to tell them apart. The compiler therefore appends the parameter types to the name, which is called name mangling. The resulting name is the symbol: the name the linker uses to match a call with the function body. If a symbol cannot be found you get an undefined reference error. For example, if a sketch has no setup(), the linker reports undefined reference to `setup', because the core's main() calls it and finds nothing.

Hands-on

This sketch proves that three info functions can live side by side (the compiler picks one by its parameters), and that an enum class refuses to become a number by itself.

  1. Create a new sketch, paste the code below, save it as logx, and press Upload.
  2. Open Tools → Serial Monitor at 115200 baud. If nothing appears, press reset on the board once.
logx.ino
#include <Adafruit_TinyUSB.h>   // enables USB and Serial (required by this core)
namespace logx {
void info(const char* msg) {
  Serial.print("[I] "); Serial.println(msg);
}
void info(const char* key, int value) {
  Serial.print("[I] "); Serial.print(key); Serial.print('='); Serial.println(value);
}
void info(const char* key, float value, int digits = 2) {   // default argument
  Serial.print("[I] "); Serial.print(key); Serial.print('='); Serial.println(value, digits);
}
}  // namespace logx

enum class Mode : uint8_t { Off, Slow, Fast };

void setup() {
  Serial.begin(115200);
  while (!Serial) {}
  logx::info("boot");
  logx::info("uptime_ms", (int)millis());
  logx::info("vbat", 3.71f);
  logx::info("pi", 3.14159f, 4);
  Mode m = Mode::Slow;
  logx::info("mode", static_cast<int>(m));   // explicit cast required
  // int bad = m;   // uncomment this line: compile error
}

void loop() {}

Reading the code piece by piece:

  • const char* msg: the text "boot" is stored as an array of char ending in '\0' ('b' 'o' 'o' 't' '\0'). Passing it to a function does not copy the text; only the address of the first character is passed. char* is a pointer holding that address, and const means the function may only read it. Plain char msg would not work: a char holds one character ('b'), so info("boot") would fail to compile.
  • millis(): an Arduino core function, like delay(), available in every sketch without any include. It returns the milliseconds since the board started, as a uint32_t (an unsigned 32-bit integer). You will use it for real in lessons 07–08.
  • (int)millis(): (int) is a C-style cast. It is needed because logx::info has one version taking int and one taking float. Pass a uint32_t directly and the compiler could convert it to either, cannot choose, and reports error: call of overloaded 'info(...)' is ambiguous. The largest positive value an int holds is about 24.8 days of milliseconds; after that it turns negative, which does not matter here.
  • default argument: int digits = 2 means 2 is used when the caller leaves it out.
  • static_cast<int>(m): the C++ cast. It does what C's (int)m does, but makes the intent obvious.

Expected output (the uptime_ms number depends on when you open Serial Monitor):

Serial Monitor
[I] boot
[I] uptime_ms=1234
[I] vbat=3.71
[I] pi=3.1416
[I] mode=1

What the output tells you:

  • overloading: every line calls the same logx::info, yet the format differs by parameters. vbat gets 2 decimals from the default argument; pi gets the 4 you passed.
  • enum class: mode=1 because Slow is the second value (counting from 0), but you had to convert it with static_cast. Remove the // in front of int bad = m; and press Verify: you get error: cannot convert 'Mode' to 'int' in initialization. Then put the // back.
  • ambiguous: remove the (int) in front of millis() and press Verify. The error says the call of overloaded info is ambiguous. Then put (int) back.

Check your understanding

How do you include a library written in C?

Wrap the header in extern "C" { … } to turn off name mangling for those functions, so the linker finds the C-style symbol names. Without it you get undefined reference errors.

If you add int info(const char* msg), which differs from the existing one only in its return type, will it compile?

No. A call like info("boot") only shows the compiler the arguments, which are the same for both, so it cannot tell them apart. An overload must differ in its parameters.

Should an LED pin number be an enum class or a constexpr?

constexpr. A pin is a number you pass straight to digitalWrite(); as an enum class you would need a static_cast every time. Enums suit a set of meaningful choices, such as modes or states.
