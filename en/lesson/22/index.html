CI 2: compile the firmware in CI

30 min · Hardware: Computer

In this lesson

  2. Step 2: Add the build-firmware job
  3. Step 3: Require PRs to pass CI
  4. Check your understanding

Goal Add a job that compiles the firmware after the tests pass, and require PRs to pass CI before merging

The last lesson's CI tests the logic, but nobody checks yet that the whole firmware compiles. This lesson proves that the firmware builds on a clean machine that is not yours (not just "works on my PC"), and that a PR that breaks the build cannot be merged.

Step 1: Find the FQBN with arduino-cli

CI has no Arduino IDE to click, so it uses arduino-cli, Arduino driven by typed commands (Arduino IDE 2 itself runs arduino-cli behind the scenes). It needs the board's full name, the FQBN (Fully Qualified Board Name), in the form vendor:architecture:board. The first line of the verbose output in lesson 01 shows it too.

  1. Arduino IDE 2 ships with arduino-cli and shares the core you installed in lesson 00. Open PowerShell and run the command below (if the IDE is installed elsewhere, adjust the path).
  2. Find the Seeed XIAO nRF52840 Sense line. Its FQBN is Seeeduino:nrf52:xiaonRF52840Sense. If your board is not the Sense model, use that model's value instead.

macOS / Linux, or not using Arduino IDE 2: download arduino-cli from github.com/arduino/arduino-cli/releases and run core install Seeeduino:nrf52 --additional-urls … before board listall, as in the Install board core step of ci.yml below.

PowerShell
& "C:\Program Files\Arduino IDE\resources\app\lib\backend\resources\arduino-cli.exe" board listall xiao
Expected output
Board Name                     FQBN
Seeed XIAO nRF52840            Seeeduino:nrf52:xiaonRF52840
Seeed XIAO nRF52840 Plus       Seeeduino:nrf52:xiaonRF52840Plus
Seeed XIAO nRF52840 Sense      Seeeduino:nrf52:xiaonRF52840Sense
Seeed XIAO nRF52840 Sense Plus Seeeduino:nrf52:xiaonRF52840SensePlus

Step 2: Add the build-firmware job

  1. In Git Bash, create a new branch, open .github/workflows/ci.yml and replace its content with the file below (the env: section and the build-firmware job are new). If the FQBN from step 1 differs from the one in the file, change it to match.
  2. Commit, push, open a PR and wait for both jobs to turn green. The second job takes longer because it downloads the core.
  3. Open the run in the Actions tab, scroll to the Artifacts section, download firmware and check that it contains a .hex and a .zip.
  4. Merge the PR.
.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

env:
  BOARD_URL: https://files.seeedstudio.com/arduino/package_seeeduino_boards_index.json
  FQBN: Seeeduino:nrf52:xiaonRF52840Sense   # use the value from board listall

jobs:
  host-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build tests
        run: g++ -std=c++17 -Wall -Wextra -Werror -Ifirmware/src test/test_main.cpp -o test_runner
      - name: Run tests
        run: ./test_runner
      - name: Static analysis
        run: |
          sudo apt-get update && sudo apt-get install -y cppcheck
          cppcheck --error-exitcode=1 --enable=warning,performance --std=c++17 -Ifirmware/src test/test_main.cpp

  build-firmware:
    needs: host-tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install adafruit-nrfutil   # the core needs it to package the .zip on Linux
      - uses: arduino/setup-arduino-cli@v2
      - name: Install board core
        run: |
          arduino-cli core update-index --additional-urls "$BOARD_URL"
          arduino-cli core install Seeeduino:nrf52 --additional-urls "$BOARD_URL"
      - name: Compile
        run: arduino-cli compile --fqbn "$FQBN" --additional-urls "$BOARD_URL" --output-dir out firmware
      - uses: actions/upload-artifact@v4
        with:
          name: firmware
          path: out/

What is new since lesson 21:

  • env:: variables shared by every job, used in commands as "$BOARD_URL" and "$FQBN", so you change them in one place.
  • needs: host-tests: this job waits until host-tests has passed.
  • setup-python + pip install adafruit-nrfutil: the tool the core uses to package the .zip for the bootloader (lesson 23); on Linux you install it yourself.
  • setup-arduino-cli and the Install board core step install arduino-cli and the Seeed core every time, because the runner is a clean machine. It is the same as Boards Manager in lesson 00.
  • Compile is the IDE's Verify button as a command. --output-dir out puts the results (.hex, .zip) in an out folder.
  • upload-artifact stores the out folder with that run under the name firmware. Files produced by a build like this are called artifacts.
Git Bash
git switch -c ci/build-firmware
# edit ci.yml and save, then:
git add .github/
git commit -m "ci: compile firmware after host tests"
git push -u origin ci/build-firmware
gh pr create --fill
gh pr checks --watch

Step 3: Require PRs to pass CI

  1. On GitHub, go to Settings → Branches and edit the main rule you created in lesson 18.
  2. Turn on Require status checks to pass before merging, search for and add host-tests and build-firmware, and save.
  3. Add a CI status badge at the top of the README (replace <user> with your GitHub account name) and commit it through a PR.
README.md
![CI](https://github.com/<user>/xiao-embedded-cpp/actions/workflows/ci.yml/badge.svg)

If the CI compile fails at the packaging step, check that adafruit-nrfutil is installed and that the FQBN matches what arduino-cli board listall xiao shows. Pin the core version with Seeeduino:nrf52@x.y.z so builds are reproducible.

Check your understanding

What is needs: host-tests for?

build-firmware runs only after the tests pass, which saves time and makes the order of priority clear. Without it, the two jobs run in parallel.

Why pin the core and action versions?

So that building again at any time gives the same firmware. If the core updates itself, the firmware may behave differently without anyone touching the code. It is the same idea as locking part numbers in a hardware BOM (bill of materials).

In practice

Teams often mix up CI and CD: CI = integrate code often and check it automatically every time; CD = deliver ready-to-use artifacts automatically (next lesson). Keeping them apart makes pipeline discussions easier.
