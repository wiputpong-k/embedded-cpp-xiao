Module B · Git and GitHub

Pull Request

25 min · Hardware: Computer

In this lesson
  1. Hands-on: your first PR
  2. Protect main
  3. Check your understanding

Goal Work through Pull Requests like a real team, and set a rule so main only changes through PRs

A Pull Request (PR) is a request to merge one branch into main on GitHub. It has a page that shows the diff for others to read and comment on, and it is where CI checks the code automatically before the merge. Even when you work alone, going through PRs leaves a record of why each change was made.

Hands-on: your first PR

  1. Create a new branch, then create README.md in the repo folder (open it with VS Code or Notepad). Write briefly what the project is, which pins it uses and how to build it.
  2. Commit, push the branch to GitHub, and open a PR with gh pr create --fill (it uses your commit message as the PR title and description).
  3. Run gh pr view --web to open the PR in your browser. Look at the Files changed tab and leave one comment on a line.
  4. Merge the PR with a squash merge, then switch back to main locally and pull the result.
terminal
git switch -c docs/readme
# write README.md: wiring photo, build steps, pins used
git add README.md
git commit -m "docs: add README with wiring and build steps"
git push -u origin docs/readme
gh pr create --fill
gh pr view --web
# leave one review comment on the web, then continue
gh pr merge --squash --delete-branch
git switch main
git pull

Protect main

  1. On the repo page on GitHub, go to Settings → Branches.
  2. Add a rule for the main branch (the button is Add branch ruleset or Add classic branch protection rule; the exact label changes from time to time as GitHub updates the page).
  3. Turn on Require a pull request before merging and save.

Do not turn on required status checks yet, because there is no CI. You come back to it in lesson 22. This rule is free for public repos.

Check your understanding

What is good about a squash merge?

It combines the PR's small commits into one commit on main: readable history, 1 commit = 1 feature, easy to revert.

Why use PRs when you work alone?

A PR is where CI checks the code before it reaches main, and it keeps the what-and-why of each change in one place, easy to look up or revert later.

In practice

On a team, a README with a wiring photo, a green CI badge and a clean commit history lets teammates, or whoever takes over the project, set up and understand it in minutes instead of asking one question at a time.
