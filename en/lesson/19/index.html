Module C · Testable code and CI/CD

Separate logic from hardware + run tests on a PC

30 min · Hardware: Computer

In this lesson
  1. Step 1: Install g++
  2. Step 2: Add the test file and run it

Goal Install g++ and run the Debouncer and RingBuffer tests on a PC in seconds, with no board plugged in

The Debouncer and RingBuffer never call the Arduino API. The Debouncer takes the time as a parameter (nowMs) instead of calling millis() itself. This is the simplest form of dependency injection: it lets g++ compile the code on a PC, and lets a test control time down to the millisecond.

Step 1: Install g++

Windows has no C++ compiler built in. The recommended way to get one is MSYS2.

  1. Open msys2.org, download the installer (msys2-x86_64-….exe) and install with the defaults. You get a C:\msys64 folder.
  2. Open MSYS2 UCRT64 from the Start menu and run the first command below. When asked to confirm, press Enter or type Y.
  3. Let Git Bash find g++: press the Windows key, type Edit environment variables for your account, pick Path → Edit → New, enter C:\msys64\ucrt64\bin and click OK on every window.
  4. Close Git Bash, open it again and run g++ --version. You should see a version number.

macOS: run xcode-select --install, which gives you a compiler you can call as g++. Linux (Ubuntu): run sudo apt install g++.

MSYS2 UCRT64
pacman -S mingw-w64-ucrt-x86_64-gcc

Step 2: Add the test file and run it

  1. In Git Bash, go into the repo and create a test folder (the first 2 lines below).
  2. Run notepad test/test_main.cpp (or code), paste the test/test_main.cpp code below and save.
  3. Run the g++ command, then ./test_runner. You should see ALL TESTS PASSED.
  4. Commit the test file.

-Ifirmware/src tells g++ to look for headers in that folder, so the test includes the very same Debouncer.h and RingBuffer.h the board uses. -Wall -Wextra -Werror turns on all warnings and treats them as errors.

Git Bash
cd ~/xiao-embedded-cpp
mkdir test
g++ -std=c++17 -Wall -Wextra -Werror -Ifirmware/src test/test_main.cpp -o test_runner
./test_runner
# ALL TESTS PASSED
git add test/
git commit -m "test: add host unit tests"
test/test_main.cpp
#include <cstdio>
#include <cstdlib>
#include "RingBuffer.h"
#include "Debouncer.h"

static int failures = 0;
#define CHECK(cond)                                                    \
  do {                                                                 \
    if (!(cond)) {                                                     \
      std::printf("FAIL %s:%d  %s\n", __FILE__, __LINE__, #cond);      \
      ++failures;                                                      \
    }                                                                  \
  } while (0)

static void test_ringbuffer() {
  xiao::RingBuffer<int, 3> rb;
  CHECK(rb.size() == 0);
  CHECK(rb.push(1) && rb.push(2) && rb.push(3));
  CHECK(!rb.push(4));          // already full
  int v = 0;
  CHECK(rb.pop(v) && v == 1);  // FIFO: first in, first out
  rb.pushOverwrite(4);
  rb.pushOverwrite(5);         // full → drops 2
  CHECK(rb.at(0) == 3 && rb.at(2) == 5);
  CHECK(average(rb) == 4.0f);
}

static void test_debouncer() {
  using E = Debouncer::Event;
  Debouncer d(20);
  CHECK(d.update(true, 0) == E::None);   // press starts
  CHECK(d.update(false, 5) == E::None);  // bounce
  CHECK(d.update(true, 8) == E::None);   // bounce
  CHECK(d.update(true, 20) == E::None);  // stable for only 12 ms
  CHECK(d.update(true, 28) == E::Pressed);
  CHECK(d.isPressed());
  CHECK(d.update(true, 40) == E::None);  // held down, no repeat event
}

int main() {
  test_ringbuffer();
  test_debouncer();
  if (failures == 0) std::puts("ALL TESTS PASSED");
  return failures == 0 ? EXIT_SUCCESS : EXIT_FAILURE;
}

Check your understanding

Why does the exit code matter?

CI decides pass/fail from each command's exit code: 0 = pass, anything else = fail, which stops the pipeline. That is why test_main.cpp returns EXIT_FAILURE when any CHECK fails.

Why can tests on a PC be trusted when they never touch the board?

The tests compile the same headers as the real firmware and exercise pure logic. The hardware-dependent parts (reading pins, real timing) still need separate tests on the board.
