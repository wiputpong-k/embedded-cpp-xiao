Install Git and make your first commit

Goal Install Git, then put all your work so far into a repo, with commit messages that make sense

Git keeps the history of your code. Every commit is a snapshot of all your files at that moment, which you can always look back at or restore. You use it from this lesson to the end of the course.

Step 1: Install Git

  1. (Optional) If you want VS Code as your text editor, install it first from code.visualstudio.com, because the Git installer looks for it.
  2. Open git-scm.com/downloads/win and download the 64-bit Git for Windows installer.
  3. Run the installer and click Next through the defaults, except on these two pages:
    • Choosing the default editor used by Git: pick Use Visual Studio Code as Git's default editor if you installed VS Code, or Use Notepad as Git's default editor if you did not.
    • Adjusting the name of the initial branch: pick Override the default branch name and type main.
  4. Click Install and wait until it finishes.

Why choose an editor? Some Git commands open a text editor for you to type in, such as git commit without -m, or a merge in lesson 16. Git's default is Vim, which newcomers often cannot figure out how to exit. VS Code or Notepad is easier. Either one works for this course.

Step 2: Open Git Bash and tell Git who you are

The Git installer includes Git Bash, a terminal that uses the same commands as Linux and macOS. Type every command from this lesson on in Git Bash (press the Windows key, type Git Bash, press Enter). On macOS and Linux, use the normal Terminal.

Run the first 3 lines of the commands below with your own name and email. They are attached to every commit and become public when you push to GitHub. If you do not want to expose your real email, use the noreply address GitHub gives you (GitHub → Settings → Emails).

Check: git --version prints something like git version 2.xx.x.windows.1.

Git Bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git --version

Step 3: Create the repo and bring in your work from lessons 13–14

  1. Run the commands below one line at a time. You get a xiao-embedded-cpp folder in your home folder (~) with an empty Git repo.
  2. The cp -r line copies the firmware sketch from lessons 13–14 in. If your sketches are not in Documents/Arduino, check the real location in Arduino IDE under File → Preferences → Sketchbook location (with OneDrive it is often ~/OneDrive/Documents/Arduino).
Git Bash
cd ~
mkdir xiao-embedded-cpp
cd xiao-embedded-cpp
git init
cp -r ~/Documents/Arduino/firmware .
ls firmware firmware/src

Step 4: Tell Git which files to ignore

Files that a build can regenerate, such as .hex files or the test program, do not belong in the repo. Run notepad .gitignore (or code .gitignore if you use VS Code). If it asks whether to create a new file, answer Yes, paste the content below, save and close.

.gitignore
build/
*.hex
*.zip
*.uf2
firmware/src/version.h
test_runner
test_runner.exe
.vscode/

Step 5: Your first commit

git status shows what changed, git add puts files into the staging area, and git commit stores them as a permanent snapshot.

Git Bash
git status
git add .gitignore firmware/
git commit -m "feat: led, debouncer, ring buffer and task scheduler"
git log --oneline

# edit a file, then try:
git diff              # changes not yet added
git add -p            # add chunk by chunk
git restore <file>    # discard changes not yet added

Try changing a number in tasks[] in firmware/firmware.ino, run git diff to see the change, then run git restore firmware/firmware.ino to throw it away.

The commit message style most teams use (Conventional Commits): feat: new feature, fix: bug fix, docs:, test:, ci:, refactor:. One commit = one topic.

Check your understanding

Why should you not commit .hex files?

They are build output you can regenerate from source. They change on every build, bloat the repo and make diffs unreadable. Binaries belong in a GitHub Release (lesson 23).

How do git add . and git add -p differ?

add . takes every change; -p lets you pick hunk by hunk, so you can split commits by topic even when one file has several changes.
