Module A · C++ for C programmers

.ino is C++, and the path from code to board

25 min · Hardware: Board only

In this lesson
  1. Hands-on
  2. Check your understanding

Goal See what Arduino hides from you, and the real toolchain

On a computer, a C/C++ program starts at main(), which the OS calls. A microcontroller (MCU: a single chip with CPU, memory and I/O pins built in, like the nRF52840 on the XIAO) has no OS to call it. So why does an Arduino sketch have no main()? Because Arduino hides it from you.

A .ino file is not a special language. The IDE only adds #include <Arduino.h> and function prototypes, then hands the file to arm-none-eabi-g++ to compile as ordinary C++. The terms in that paragraph:

  • toolchain: the set of programs that turns code into a file the chip can run (compiler, linker, file converters). The IDE runs them when you press Verify.
  • arm-none-eabi-g++: a cross-compiler version of g++. It runs on your PC but produces code for another CPU: arm = the ARM CPU family (the nRF52840 is a Cortex-M4F), none = no OS, eabi = ARM's embedded standard for calling functions and laying out data.
  • core: code the vendor provides for that chip, with main(), digitalWrite(), Serial and so on. It is what you installed from Boards Manager in lesson 00.
  • function prototype: a line that declares a function ahead of time, e.g. void blink(int ms);. C++ requires a declaration before a call. In a .ino you can put functions at the end of the file because the IDE writes these lines for you.

The real main() lives in the core:

core/main.cpp (trimmed)
int main() {
  init();          // clock, timer, USB CDC
  setup();
  for (;;) {
    loop();
  }
}

On power-up or reset, the chip enters the core's main(). It calls init() to prepare the hardware, calls setup() once, then calls loop() forever, because firmware has no OS to "return to". What init() prepares:

  • clock: the timing signal that drives the CPU and other circuits (64 MHz on the nRF52840). It must be set up first.
  • timer: a counting circuit in the chip. millis() and delay() are built on it.
  • USB CDC: makes the board appear as a virtual serial port over USB (the COM port you see in Windows). Serial Monitor talks to the board through it.

The real nRF52 core runs setup()/loop() inside a FreeRTOS task (a small OS for MCUs) and does more steps, but the order init → setup → loop is the same.

The files and tools in the figure:

  • .o (object file): one source file after compiling. It is ARM machine code, but it has no final addresses yet and cannot call functions in other files.
  • linker: combines all .o files with core.a (the precompiled core) and libraries, and connects calls between files.
  • linker script: tells the linker where flash and RAM start, how big they are, and where code and variables go.
  • .elf: the linker's output, holding the code plus debug symbols (function and variable names, line numbers).
  • objcopy: keeps only the bytes to be written to the chip (.hex, .uf2). Then the upload, or flash, step hands the file to the bootloader (a small program on the chip that receives new firmware), which writes it into memory.

Hands-on

  1. Open Arduino IDE, select the board and port as in lesson 00, and create a new sketch (File → New Sketch). Replace its contents with the code below and save it as whoami.
  2. Press Upload and wait until the Output panel shows Device programmed or the upload finishes.
  3. Open Tools → Serial Monitor and set the speed at the right to 115200 baud. If nothing appears, press reset on the board once.
whoami.ino
#include <Adafruit_TinyUSB.h>   // enables USB and Serial (required by this core)
void setup() {
  Serial.begin(115200);
  while (!Serial) {}             // wait for USB CDC
  Serial.print("__cplusplus = ");  Serial.println(__cplusplus);
  Serial.print("sizeof(int) = ");  Serial.println(sizeof(int));
  Serial.print("sizeof(void*) = ");Serial.println(sizeof(void*));
  Serial.print("sizeof(bool) = "); Serial.println(sizeof(bool));
}

void loop() {}
  • Serial.begin(115200) opens serial at 115200 baud (bits per second). Over USB CDC the number has no real effect, but make a habit of matching it in Serial Monitor, because a wired serial port (UART) needs both sides to agree.
  • while (!Serial) {} waits until the computer opens the port. Otherwise the text is sent before Serial Monitor opens and is lost.
  • sizeof(x) gives the size of a type in bytes.

Expected output:

Serial Monitor
__cplusplus = 201103
sizeof(int) = 4
sizeof(void*) = 4
sizeof(bool) = 1

__cplusplus tells you the language standard the compiler uses (201103 = C++11, 201703 = C++17). Note it down, because the features you can use depend on it. int and pointers are 4 bytes because the Cortex-M4F is a 32-bit CPU. On an Arduino Uno (8-bit), int is only 2 bytes, so embedded code should not assume the size of int.

Finally, read the last lines of the Output panel after Verify or Upload:

  • Sketch uses … bytes = program size in flash, the permanent memory that holds the program and survives power-off (the nRF52840 has 1 MB, but part is reserved for the bootloader and the BLE stack, so the Maximum shown is smaller).
  • Global variables use … = static RAM, the working memory (256 KB) that is lost at power-off. "Static" means its size is known at build time: the global variables. The rest of RAM is used for the stack (local variables) and the heap.

Check your understanding

If __cplusplus is 201103, can you use if constexpr?

No. if constexpr is C++17. Add -std=gnu++17 or fall back to template overloads.

Does "Global variables use" include the stack?

No. It counts only .data (globals with an initial value) + .bss (globals that start at 0), whose sizes are known at link time. Local variables on the stack are not in that number.

In practice

When a build breaks, walk the stages in order: preprocess → compile → link (the linker script sets the addresses) → objcopy → flash, and you will see where it failed. Always keep the .elf: it carries the debug symbols the debugger needs, while the .hex/.bin is the image that goes onto the chip.
