Interrupts, volatile and lambdas

30 min · Hardware: Button on D1

In this lesson
  1. Hands-on
  2. Check your understanding

Goal Write a correct ISR, and share data between the ISR and loop safely

Lesson 07 read the button by checking it in every loop() pass (polling). If loop is stuck in delay(), a short press can be missed. The alternative is to let the hardware call your code the moment the pin changes. Terms in this lesson:

  • ISR (Interrupt Service Routine): the function the CPU jumps to as soon as an interrupt (lesson 06) happens. When it finishes, the CPU resumes exactly where it left off, as in the figure.
  • FALLING: the moment a pin goes from HIGH to LOW, i.e. when the button starts being pressed, because it is wired with INPUT_PULLUP (lesson 07).
  • volatile: normally the compiler may keep a variable in a CPU register and not re-read RAM. If an ISR changes the value in RAM, loop may never see it. volatile forces a real RAM read and write every time.
  • atomic: an operation that cannot be cut in the middle. noInterrupts() / interrupts() turn interrupts off and on so the code between them is atomic (like CriticalSection, lesson 06).
  • lambda: an unnamed function written right where it is used, in the form [] { … }. The empty [] means it uses no local variables from outside, so it can be passed to attachInterrupt as a function pointer.

Hands-on

This sketch proves that the ISR cuts in by itself even while loop() is waiting in delay(500), and shows why an ISR on a button still needs debouncing. It uses the button on D1 from lesson 07.

  1. Create a new sketch, paste the code below, save it as isr_count, and press Upload.
  2. Open Tools → Serial Monitor at 115200 baud. A number appears every half second.
  3. Press the button once at a time, then try 3 quick presses within half a second.
isr_count.ino
#include <Adafruit_TinyUSB.h>   // enables USB and Serial (required by this core)
constexpr uint8_t kButtonPin = D1;
volatile uint32_t pressCount = 0;   // volatile: changes outside normal flow, never cache

void setup() {
  Serial.begin(115200);
  pinMode(kButtonPin, INPUT_PULLUP);
  // a capture-less lambda converts to a function pointer
  attachInterrupt(digitalPinToInterrupt(kButtonPin), [] {
    pressCount = pressCount + 1;
  }, FALLING);
}

void loop() {
  uint32_t count;
  noInterrupts();          // copy it out atomically
  count = pressCount;
  interrupts();
  Serial.println(count);
  delay(500);
}

attachInterrupt(pin, function, mode) calls the function whenever the pin changes in the given way. digitalPinToInterrupt() turns a pin number into the interrupt number the core uses.

What the result tells you:

  • The ISR cuts in at any moment: press 3 times within half a second and the number rises by at least 3, even though loop() sat in delay() the whole time. Polling as in lesson 07 combined with delay(500) would miss most of those presses.
  • Debouncing is still needed: one press often adds more than 1. That is the bounce from lesson 07: the bouncing contacts produce several FALLING edges. An ISR on a mechanical button therefore needs time-based debouncing, e.g. checking millis() in the ISR, or letting the ISR only notify loop and leaving the rest to Debouncer.

On a Cortex-M, a single read of a 32-bit variable cannot be cut in the middle anyway. But when you read several variables together, or modify a value with ++, always wrap it in noInterrupts(). The example wraps it to build the habit.

Check your understanding

Does volatile make pressCount++ safe from being interrupted?

No. volatile only forces a real RAM read/write every time, but ++ is three instructions (read, add, write back), and an ISR can cut in between them. Wrap it with noInterrupts() or a CriticalSection, or use std::atomic.

What must you never do in an ISR?

delay(), Serial.print(), malloc/new, long work, or functions that break when called while already running (e.g. one that loop was in the middle of when the ISR cut in). Let the ISR set a flag or push into a buffer, and return as fast as possible.

In practice

A missing volatile often works while the compiler barely optimizes, then breaks as optimization increases (this core uses -Ofast; see the verbose output, lesson 01). Remember the three cases that need it: variables changed by an ISR, hardware registers read through an address, and variables shared between tasks. And remember that volatile does not stop code being cut in the middle.
