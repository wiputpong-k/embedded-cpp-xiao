เป้าหมาย เข้าใจว่า test_main.cpp ทำงานอย่างไร ทำให้ test แดงเป็น และเพิ่ม test ใหม่เองได้

test_main.cpp ทำงานอย่างไร

  • CHECK(cond) เป็น macro ที่ถ้า cond เป็นเท็จ จะพิมพ์ชื่อไฟล์ (__FILE__) เลขบรรทัด (__LINE__) และตัวเงื่อนไขเป็นข้อความ (#cond) แล้วนับจำนวนที่ fail ไว้
  • ครอบด้วย do { … } while (0) เพื่อให้ macro ใช้ได้เหมือนคำสั่งเดียว แม้วางอยู่ใน if ที่ไม่มีวงเล็บปีกกา
  • แต่ละ test เป็นฟังก์ชันแยก (test_ringbuffer, test_debouncer) main() เรียกทุกตัว แล้วคืน exit code ตามผล
  • test_debouncer ส่งเวลาปลอม 0, 5, 8, 20, 28 ms เข้าไปเอง จึงทดสอบกรณีเด้งได้แม่นยำทุกครั้ง ซึ่งทำบนบอร์ดจริงด้วยมือแทบไม่ได้

Hands-on 1: ทำให้ test แดง

  1. เปิด firmware/src/Debouncer.h แก้ >= stableMs_ เป็น > stableMs_
  2. compile และรัน test ใหม่ (คำสั่งเดียวกับบท 19) จะเห็นบรรทัด FAIL … บอกไฟล์และเลขบรรทัดที่พัง และไม่มีข้อความ ALL TESTS PASSED
  3. รัน echo $? ทันทีหลังรัน test จะเห็นเลข 1 (exit code ของการ fail)
  4. แก้กลับเป็น >= แล้วรันใหม่ให้ผ่าน

Hands-on 2: เพิ่ม test ของคุณเอง

เพิ่มฟังก์ชันข้างล่างไว้เหนือ main() ใน test/test_main.cpp แล้วเพิ่มบรรทัด test_average_empty(); และ test_debouncer_release(); ใน main() ต่อจาก test เดิม รันให้ผ่าน แล้ว commit

test/test_main.cpp
static void test_average_empty() {
  xiao::RingBuffer<int, 4> rb;
  CHECK(average(rb) == 0.0f);      // ว่าง → 0 ไม่หารด้วยศูนย์
}

static void test_debouncer_release() {
  using E = Debouncer::Event;
  Debouncer d(20);
  d.update(true, 0);
  CHECK(d.update(true, 20) == E::Pressed);
  CHECK(d.update(false, 30) == E::None);      // เพิ่งปล่อย ยังไม่นิ่ง
  CHECK(d.update(false, 50) == E::Released);  // นิ่งครบ 20 ms
  CHECK(!d.isPressed());
}

ในงานจริงใช้ framework เช่น GoogleTest, Catch2 หรือ Unity (สำหรับ C) แต่หลักการเหมือนกัน: CHECK เงื่อนไข, รายงานบรรทัดที่พัง, exit code ≠ 0 เมื่อ fail เพื่อให้ CI รู้

เช็กความเข้าใจ

จะ test โค้ดที่เรียก digitalRead() ได้อย่างไร?

ซ่อนการเข้าถึงฮาร์ดแวร์ไว้หลัง interface (เช่น ISensor บท 09) แล้วใส่ fake/mock ตอน test หรือส่งค่าที่อ่านได้เข้าฟังก์ชันแทนให้ฟังก์ชันไปอ่านเอง

test ที่ดีควรเป็นอย่างไร?

เร็ว ผลเหมือนเดิมทุกครั้ง ทดสอบทีละเรื่อง และอ่านแล้วรู้ว่าคาดหวังอะไร รวมถึงกรณีขอบ เช่น buffer ว่าง buffer เต็ม และเวลา overflow

มุมงานจริง

ทีม firmware ส่วนใหญ่ test เป็นชั้น: unit test บน host สำหรับ logic, HIL test บนบอร์ดจริงสำหรับ driver, system test สำหรับฟีเจอร์ ชั้นแรกเร็วและถูกที่สุด จึงรันใน CI ทุก commit
